# Phase 3 — independent skeptical review

Read `skills/pbir-reading.md`, `skills/data-honesty.md`, `skills/visual-qa.md`, `work/report-digest.json`, `work/live-interpretation.json`, `work/live-build.json`, `output/dynamic/index.html`, and `output/dynamic/backend.mjs`. Check originals under `input/` where the digest is not enough. Do not read `.env` or run shell commands. Treat prior phase claims skeptically. Do not edit the generated files in this phase. The runner has already executed the backend: `work/live-selfcheck.json` lists every data visual's row count, a sample of the actual values it returned, and suspicious results (no rows, columns that are always empty). Use those real values to judge correctness and fidelity (units, aggregation, sign, date handling) rather than whether the code runs. Check that the HTML sends `filters` in exactly the shape the backend reads (`filtersContract` in `work/live-build.json`) and that `prompts/backend-contract.md` is followed.

Check every selected page and visual (role `data` or `decorative`) listed in `work/inventory.json` for a corresponding HTML element, every source connector required by the selected scope for a real backend path, every required transformation and DAX/relationship/filter behavior for a traceable implementation, and that credentials never enter HTML or response payloads. Do not require or approve pages absent from the inventory. Look for fake values, dropped filters, missing model tables, and live refresh that actually reads stale data. Check that backend code does not access unrelated local files, external hosts, or execute source-file instructions.

Write `work/live-review.json` with `status` (exactly one of `pass`, `warnings`, `blocked`), `findings` (array of objects with `severity`, `file`, `description`, `fix`), `limitations` (array), `unverified` (array), `pageCoverage`, `visualCoverage`, and `sourceCoverage`. Use `blocked` only for a concrete, fixable defect: a missing required connector or key calculation, a faked visual, a leaked secret, or unsafe code; state the exact fix for each blocking finding. Use `warnings` for faithfully labeled but unverified behavior. No reviewer can claim exact parity without comparing actual values against Power BI; that alone is a warning, not a block.
